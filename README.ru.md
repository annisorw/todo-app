# Aurora Tasks

Быстрый, анимированный список задач, который работает целиком в браузере. Нет аккаунта,
нет сервера, нет синхронизации — каждая задача хранится в `localStorage` вашего браузера,
на вашей машине. Продукт для одного человека, которому нужен спокойный, удобный с
клавиатуры список на день или неделю, а не командный трекер задач.

> **Черновик.** Этот README — черновик по состоянию текущей ветки `main`, написанный до
> завершения основной задачи документации (FELA-24). Скриншоты и ссылка на демо —
> заглушки до тех пор, пока та задача не будет сделана. Раздел «Возможности» ниже
> отмечает, что из этого уже есть в `main`, а что ещё в работе, — так эта страница не
> обещает больше, чем приложение умеет сейчас.

## Стек и почему он такой

| Решение | Значение | Почему |
|---|---|---|
| UI | React 19 + TypeScript (strict) | уже в репозитории |
| Сборка | Vite 8 | уже в репозитории |
| Стили | Tailwind CSS v4 поверх слоя CSS-токенов | утилиты быстрые, но значение всё равно обязано приходить из токена, а не быть числом в коде |
| Анимации | Framer Motion | уже в репозитории |
| Тесты | Vitest + Testing Library + jsdom | уже в репозитории |
| Данные | `localStorage`, без сервера | сервера нет по условию |

Новая runtime-зависимость не ставится без причины, записанной в задаче, и ревью
TechLead/Security — см. `docs/ARCHITECTURE.md` §1. Это осознанно держит дерево
зависимостей маленьким («boring technology»), а вместе с ним и поверхность атаки.

## Быстрый старт

### Требования

- Node.js 24 или новее (проект собирается и тестируется на `v24.21.0`)
- npm (идёт вместе с Node.js)

### Установка

```bash
npm install
```

### Запуск локально

```bash
npm run dev
```

Поднимает дев-сервер Vite и печатает локальный адрес (обычно `http://localhost:5173/`).
Откройте его в браузере; страница перезагружается при каждом изменении файла.

### Сборка для продакшена

```bash
npm run build
```

Запускает сборку TypeScript-проекта (`tsc -b`), затем продакшен-сборку Vite. Результат —
в `dist/`. Команда падает при любой ошибке типов, поэтому она же служит финальной
проверкой типов перед релизом.

### Просмотр продакшен-сборки

```bash
npm run preview
```

Раздаёт папку `dist/`, собранную выше, так же, как это будет делать GitHub Pages.
Полезно проверить продакшен-сборку перед выкладкой: `npm run dev` использует другой путь
сборки.

### Линт и проверка типов

```bash
npm run lint       # oxlint
npm run typecheck  # tsc -b, без эмита
```

### Запуск тестов

```bash
npm run test
```

Прогоняет набор Vitest один раз (без watch-режима) и печатает число файлов и тестов,
которые прошли. Это число меняется почти с каждым PR, поэтому здесь оно не
зафиксировано — запустите команду, чтобы увидеть актуальный счёт в `main`.

Все четыре команды выше (`lint`, `typecheck`, `test`, `build`) — это и есть обязательные
проверки CI для любого pull request, см. [Вклад в проект](#вклад-в-проект).

## Структура папок

Полная версия со всей аргументацией лежит в
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md). Коротко:

```
src/
  domain/      чистый TypeScript, ни одного импорта React — модель задачи, операции
               над списком, фильтры, работа со сроком
  storage/     обёртка над localStorage, валидация схемы, запись с debounce
  state/       единственный reducer задач, провайдеры React (задачи, тема, тосты)
  components/  презентационные блоки (Button, Checkbox, Menu, Toast, ...)
  features/    экранная логика, связывающая стор и компоненты (composer, toolbar, ...)
  layout/      каркас страницы, шапка, анимированный фон, плавающая кнопка действия
  lib/         мелкие хелперы, в основном React-хуки (debounce, фокус/закрытие, ...)
  styles/      слой токенов (`tokens.css`) и глобальные стили (`base.css`)
```

Правило, которое делает это рабочим, а не декоративным: `domain/` никогда не импортирует
React, а `components/` никогда не читает состояние приложения напрямую — компонент,
которому нужен стор задач, живёт в `features/`, а не в `components/`. `ErrorBanner` (в
`components/`) — осознанное исключение: он читает `useTaskStore`/`useToast` напрямую,
потому что кнопке выгрузки нужен живой список задач и карантинная копия, которую хранит
только `storage/` — подробности в комментарии над `ErrorBanner.tsx`. `lib/` — это
«мелкие хелперы», а не «независимые от фреймворка»: большая их часть (`useDismissable`,
`useDebouncedValue`, `useMediaQuery`, ...) — React-хуки; без импорта React обходятся
только несколько модулей (`cn`, `dismissStack`, ...). Полная аргументация —
`docs/ARCHITECTURE.md` §2, правила, относящиеся к безопасности (что нельзя превращать
в HTML из текста пользователя, как обязана работать подсветка поиска и так далее) —
`docs/CODE-RULES.md`.

## Хранение данных

Всё хранится в `localStorage` браузера, в трёх ключах:

- `aurora.tasks.v1` — список задач, в виде `{ "version": 1, "tasks": Task[] }`.
- `aurora.theme` — выбранная тема, `"light"` или `"dark"`.
- `aurora.tasks.v1.corrupted` — карантинная копия сырых байт из `aurora.tasks.v1`,
  записывается только тогда, когда чтение находит их нечитаемыми (см. ниже).

Список читается один раз, синхронно, до первого рендера, и записывается обратно с
debounce 250 мс после каждого изменения. Из браузера ничего не уходит: сетевых запросов
в приложении нет вообще.

**Если сохранённые данные нечитаемы** (битый JSON, вручную испорченный файл, запись от
другой версии приложения), приложение пытается их сохранить, но это не гарантия. При
чтении оно пытается скопировать нераспознанные байты в карантинный ключ
`aurora.tasks.v1.corrupted`, прежде чем что-либо ещё коснётся `aurora.tasks.v1` — но
сама эта попытка может не удаться (квота хранилища, приватный режим, недоступное
хранилище), и тогда отказ виден только в логе разработки, а исходные байты теряются.
После этого приложение стартует с пустым списком в памяти и показывает баннер ошибки с
объяснением, что сохранённые данные не удалось прочитать. Кнопка в баннере выгружает
карантинную копию в файл только если она действительно была сохранена и до сих пор
доступна; иначе показывается тост («Выгружать нечего: повреждённые данные не
сохранились.») и файл не создаётся.

## Возможности

Что можно по-настоящему сделать в приложении на текущем `main`:

- Добавлять, редактировать, отмечать выполненными и удалять задачи через интерфейс
  (`Composer` и `TaskList` подключены в `src/App.tsx`).
- Задавать приоритет и срок для задачи — они видны как метки на строке.
- Искать и фильтровать список (все / активные / выполненные), со счётчиком на каждый
  фильтр.
- Изменить порядок активных задач, перетащив ручку строки, или с клавиатуры: `Space`
  берёт сфокусированную строку, `↑`/`↓` двигают её, `Space` отпускает (`Esc` отменяет);
  каждый шаг озвучивается для скринридеров.
- Очищать все выполненные задачи сразу, через диалог подтверждения
  (`CompletedSection`).
- Отменить удаление кнопкой «Вернуть» на тосте или глобальной комбинацией
  `Ctrl`/`Cmd+Z` — обе вызывают одно и то же действие.
- Нажать `?` или кнопку горячих клавиш в шапке — откроется панель со списком всех
  комбинаций: новая задача, поиск, фильтры, навигация по строкам, редактирование,
  удаление, отмена удаления, перемещение строки.
- Переключить тему между светлой и тёмной; выбор сохраняется и восстанавливается при
  перезагрузке (`aurora.theme`), причём нужная тема применяется до первой отрисовки, без
  вспышки неправильной темы.
- Увидеть иллюстрированное пустое состояние для пустого списка, поиска без результатов
  или полностью выполненного списка, а также отдельное состояние «до первой задачи»
  (`EmptyState`).
- Увидеть аккуратный баннер ошибки, если сохранённый на вашей машине список задач не
  читается, с кнопкой, которая выгружает карантинную копию — если она была сохранена и
  до сих пор доступна; см. [Хранение данных](#хранение-данных).

## Вклад в проект

- `main` всегда зелёная: прямых коммитов в `main` нет.
- Одна ветка на задачу, с номером задачи в имени, например `feat/FELA-15-task-list`,
  `fix/FELA-65-composer-focus`, `docs/FELA-99-readme-draft`.
- Коммиты — в стиле [Conventional Commits](https://www.conventionalcommits.org/), по
  английски, с номером задачи, например `feat: add task list reducer (FELA-9)`.
- Каждое изменение идёт через pull request. CI обязан быть зелёным: `lint`, `typecheck`,
  `test` и `build` (см. [Быстрый старт](#быстрый-старт) — это ровно те же четыре команды
  `npm run`, что выше).
- Автор не мержит свой PR сам. Проверка `review-ack` держит PR красным, пока ревьюер не
  оставит комментарий, первая строка которого — ровно `/merge-ok` (опционально
  `/merge-ok <sha>`) на актуальном коммите; любой новый пуш сбрасывает отметку.
  Механика — в `.github/workflows/review-ack.yml`, полный чек-лист PR, включая
  чек-лист безопасности из `docs/CODE-RULES.md`, — в `.github/pull_request_template.md`.
